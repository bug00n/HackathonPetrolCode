## 1. Вердикт

**В текущем виде проект не готов к самостоятельному запуску жюри.** Рабочая основа есть: пять модельных сценариев проходят, после явной подготовки актуальных данных выполняются исторический прогноз, hybrid и выбранный v2-прогноз. Основные препятствия — зависания UI, несовместимые автоматические настройки, неполная поставка и разъехавшиеся версии материалов.

Это ревью продукта и сдачи, а не повторный построчный аудит алгоритмов. Код просмотрен там, где требовалось объяснить наблюдаемое поведение. Исправления приложения, изменение моделей и отключение защит в этом ревью не выполнялись.

Приоритет финальных работ:

1. Убрать зависания и ошибки обычных действий пользователя.
2. Зафиксировать совместимые данные, модели и начальные примеры для каждого заявленного режима.
3. Сделать запуск из готовой поставки без ручного подбора ID и обучения перед показом.
4. Довести понятность UI, журнал и экспорт.
5. Обновить описание и презентацию из одной проверенной версии.
6. Проверить именно окончательный архив на отдельном окружении и провести репетицию.

**Не требуется перед сдачей:** внедрять АСУ, разрешать реальные уставки, строить новые ML-семейства, добавлять LLM, микросервисы или переписывать desktop-приложение. Подтверждённое ограничение модели не надо маскировать косметическим зелёным статусом.

### Как читать документ

- **Воспроизведено** — результат получен запуском текущей версии или проверкой конкретного файла поставки.
- **Подтверждено описанием/экраном** — установлен продуктовый пробел; это не обязательно ошибка расчёта.
- **Не проверено** — отдельный приёмочный пункт, а не утверждение о неисправности.
- **P1** — блокирует финальную готовность заявленной поставки.
- **P2** — существенно для понятности, полноты демонстрации или честности представления; устранить либо явно ограничить обещание.

Предлагаемые ниже UX-пороги и состав удобного release-пакета — критерии финализации команды, не дословные дополнительные требования организаторов.

| Режим / возможность | Фактическая готовность | Что должен понимать пользователь |
| --- | --- | --- |
| `model_demo`: нормальный режим | Расчёт готов, `hold` | Сохранить модельную рецептуру; отсутствие нового действия — правильный результат |
| `model_demo`: риск серы | Расчёт готов, `recommend` | Изменяются модельные доли, не реальные уставки |
| `model_demo`: T95 | Расчёт готов, `recommend` | Выбранный вариант проходит одновременно S, T95 и CN |

### AP-010 — P1. UI зависает при старте и переходах

**Воспроизведено.** Обычный вход на «Обзор» не даёт быстро получить отзывчивое окно. Вход через «Журнал» создаёт оболочку примерно за 0,108 с; при загрузке стадий окно снова перестаёт обрабатывать события. Пользователь наблюдал это во время аудита.

Источник: `source/ui.py`, `__init__`, `_render_overview`, `_render_stage_cards`, `_render_stage_page`; `source/ui_data.py`. Снятые стеки показывают чтение CSV, преобразование дат и перебор наблюдений в главном Tk-потоке. Самостоятельные stage snapshot заняли примерно 12,3 с для АВТ и 18,8 с для гидроочистки; на одном экране выполняется несколько таких операций. Это причина воспринимаемого «то включается, то лагает».

Первая диагностическая попытка завершилась кодом 1 без traceback; она не доказывает отдельный crash. Обычный повторный запуск был остановлен в ходе диагностики. Подтверждённая проблема здесь — блокирование UI, не установленная причина аварийного завершения.

**Исправить:** показывать оболочку до тяжёлой работы; загружать историю вне UI-потока; повторно не обрабатывать полный набор ради каждой карточки; показывать ход и результат загрузки. Не убирать проверку свежести или совместимости ради скорости.

**Приёмка:** пользователь видит оболочку и статус не позднее 3 с; во время загрузки доступны перемещение окна и навигация; есть понятный признак выполнения. Повторные переходы на уже загруженном наборе не блокируют UI на секунды. Измерить холодный старт, тёплый переход и полный исторический расчёт отдельно.

### AP-012 — P1. Старый source.zip не является полной финальной поставкой

**Воспроизведено.** Архив от 18.09 содержит 129 записей, полный исходный `materials/data.rar` размером 100 259 972 байта, но не содержит `artifacts/` и `data/processed/`. От текущей версии отличаются 33 общих текстовых файла, включая UI, контракты, main, сценарии и документацию; некоторые новые файлы текущего checkout вообще не представлены старым снимком.

В распакованном архиве пять модельных сценариев проходят. Проверка frozen-комплекта падает из-за отсутствия `artifacts/models/last_value-848324f28111/metadata.json`. Зависимости брались из имеющегося окружения — установка на новой машине этим не доказана.

**Исправить:** собрать новый release из одного финального commit. Исходники, готовые данные/модели и инструкции должны образовать понятный комплект; допустимы несколько явно связанных архивов. Жюри не должно переключаться на training commit и обучать модель ради первого показа.

**Приёмка:** удалить из контекста проверки локальный checkout автора, распаковать финальный комплект в новую папку с пробелами/кириллицей и воспроизвести заявленные режимы. Проверить SHA-256, настоящие RAR-данные вместо LFS-pointer и отсутствие внешних абсолютных путей.

### AP-013 — P1. Неверная дата ломает фоновый расчёт без ответа пользователю

**Воспроизведено на настоящем Tk.** В поле History/ML ввести `21.09.2026`, нажать расчёт. `_parse_as_of` выбрасывает ValueError; обработчик ошибки повторно разбирает то же неверное значение и тоже падает. Поток завершается, поле результата не получает нового объяснения ошибки.

**Исправить:** проверять ввод до запуска; показывать русское сообщение рядом с полем, допустимый пример и часовой пояс. Ошибка ввода не должна сохранять видимость успешно рассчитанного старого результата.

**Приёмка:** неверный формат, пустая дата, дата без timezone и дата вне доступной истории дают понятный завершённый ответ; никаких traceback в фоне. Исправление значения позволяет сразу повторить расчёт.

### AP-004 — P1. Исправление history не покрыло lifecycle hybrid

**Дополнение к существующей проблеме.** History-обработчик имеет защиту request ID и существования виджета. Но в hybrid при уходе со «Смеси» до завершения расчёта callback обращается к уже уничтоженному Text.

В скрытом настоящем Tk воспроизведён порядок: запустить hybrid → через 50 мс перейти в журнал → вернуть контролируемый ответ через 300 мс. Получено `TclError: invalid command name`, `source/ui.py:1238/1249`. Это проверка lifecycle с подменённым задержанным вычислением, не замер полноценного hybrid.

**Исправить:** актуальность запроса и сохранение результата не должны зависеть от жизни экрана. Проверить по тому же принципу закрытие окон v2, action-shadow, LIMS и legacy forecast: аналогичный риск виден в их callback, но все эти варианты отдельно не воспроизводились.

**Приёмка:** запуск → смена вкладки/закрытие диалога → завершение → возврат; повторный запуск с обратным порядком завершения. Нет TclError, чужих результатов и обновления уничтоженных полей.

### AP-014 — P1. Нет короткого корректного маршрута первого запуска

**Подтверждено README и составом файлов.** Начало README занято историей этапов. В первом блоке после `python -m venv .venv` нет активации или явного вызова созданного интерпретатора. `train` использует `<dataset_id>` без предыдущей подготовки в этом блоке. Windows-пользователь получает также Bash-примеры с `\` для продолжения строки. Готового launcher-файла нет.

**Исправить:** первые строки README — «что это», «что необходимо», «как открыть», «что должно появиться», «что делать при ошибке». Основной Windows-путь использует конкретный интерпретатор `.venv\Scripts\python.exe` и реальные файлы release; отсутствие Tk, данных или моделей объясняется до запуска. Отделить установку, обычный показ и разработческое обучение. Linux-инструкцию оставить отдельно и проверять только если Linux заявляется поддержанным.

**Приёмка:** новый человек без помощи автора за 5 минут после установки зависимостей открывает демо и получает первый понятный результат. Ни одного placeholder, ручного поиска модели, изменения JSON и checkout старого commit в основном маршруте. Однокнопочный launcher полезен, но не заменяет рабочую текстовую инструкцию.

### AP-015 — P2. UI обращается к разработчику, а не к оператору

**Подтверждено формами и текстами.** `Prepared dataset`, `Forecast artifact`, `As of (ISO timezone)`, `actionable`, `fresh/stale/missing`, `readiness` требуют знания внутренней архитектуры. Поля — свободные пути, без понятного списка совместимых примеров. Исследовательские инструменты спрятаны в раскрывающемся блоке «Источники…» на обзоре; сценарий смеси выбирается на другом экране.

**Исправить:** русские понятные названия, смысл режимов рядом с выбором, preset исторических примеров, календарь/понятный ввод даты, выбор файлов или готовых наборов. Служебные ID и hashes оставить в «Подробностях». Сценарий можно менять там, где его результат показывается. Раздел «Исследования» должен явно отделяться от основного показа.

Рекомендуемые формулировки: «Исторические данные», «Прогноз серы», «Модельное смешение», «Исследовательский прогноз», «Действия не рекомендуются», «Данные устарели», «Недостаточно данных». `abstain` объяснять: прогноз может быть рассчитан, но оснований рекомендовать действие нет.

**Приёмка:** без чтения DESIGN человек отвечает, какие данные реальные, что модельное, какой момент выбран, что означает результат и какую кнопку нажать дальше. Нет одиночных reason codes вместо объяснения.

### AP-016 — P2. У экранов разные начальные данные и неочевидный временной контекст

**Воспроизведено.** Автоматический момент — `2026-08-11T06:54:04Z`, конец таблицы качества. Телеметрия заканчивается `2026-08-06T21:00:00Z`; на АВТ 21/21 сигнал устарел примерно на 6354 минуты. Гидроочистка показывает 2 свежих и 10 устаревших сигналов. Это не обязательно неисправность анализатора — выбран момент за концом телеметрии.

Карточки состояния при этом показывают `ready`/read-only данные старого набора, который history-serving отвергает как несовместимый. Формы вспомогательных режимов подставляют другой набор и другой момент. Поэтому переход по цепочке не означает просмотр одного состояния.

**Исправить:** общий выбранный dataset/time, явные границы покрытия каждого источника и проверенный стартовый момент внутри совместного периода. Если выбран хвост без телеметрии, объяснять именно это. Не подменять фактическую свежесть зелёным статусом ради красивого старта. Показывать время данных отдельно от времени нажатия кнопки.

**Приёмка:** переходы АВТ → гидроочистка → history → hybrid сохраняют выбранное состояние либо явно сообщают о смене; режим источников виден; старый несовместимый набор не выглядит готовой текущей поставкой. После изменения полей прежний результат отмечен как устаревший до пересчёта.

### AP-017 — P2. Рецептура на экране теряет точность

**Подтверждено экраном и formatter.** `_recipe_table` округляет доли A/B до целого процента. В `blend_risk` показываются 89% / 10% / 1%, тогда как расчёт и документы используют 89,1% / 9,9% / 1%. В T95-примере 64,35% / 34,65% теряются ещё сильнее. Сумма может выглядеть корректной, но это уже другой состав.

**Исправить:** показывать достаточную точность массовых долей, единицы и массу партии; по возможности рядом абсолютные массы. Один формат чисел для таблицы, экспорта и презентации. Для `abstain` явно писать «рецептура не выбрана», не показывать нули как рекомендацию.

**Приёмка:** по показанным долям можно воспроизвести результат с заявленной точностью; для примера 100 т видны 89,1 т / 9,9 т / 1 т. Проверки качества продолжают использовать неокруглённые числа.

### AP-018 — P2. Журнал и экспорт не завершают пользовательский сценарий

**Подтверждено UI.** Слева в журнале UUID, справа — большой raw `result.json`. По списку нельзя выбрать «риск серы, сегодня, recommend»; полная цепочка агентов не представлена понятным обзором. Кнопка `export_result` сохраняет модельный `self._result`, а не произвольный текущий history/hybrid-результат. Полный ZIP поддерживается CLI, но не единым маршрутом из экрана расчёта.

**Исправить:** дата, сценарий, режим, статус и модель в списке; краткий итог по клику; отдельные подробности агентов и причины отклонения вариантов. Из результата — «Открыть этот запуск» и «Экспортировать этот расчёт». Различать краткий JSON и полный доказательный ZIP. Добавить понятную обработку ошибки записи.

**Приёмка:** после history пользователь находит именно его run_id и экспортирует именно его данные, а не последнее model_demo. В архиве есть вход, оценки, кандидаты, trace, результат и metadata. Отмена сохранения не ошибка; недоступная папка не приводит к необработанному исключению.

### AP-019 — P2. Hybrid выглядит шире, чем реально проверяет

**Воспроизведено и подтверждено контрактом.** Панель названа «АВТ → гидроочистка → смесь», но её результат — расчёт серы одной заданной рецептуры. Нет подтверждённого переноса влияния АВТ, полного паспорта T95/CN или оптимизации всей цепочки. Успешный `status=ready` может сопровождаться `constraint_status=fail` — в контрольном примере upper смеси 16,57166 мг/кг.

**Исправить:** явно подписать «условное смешение по прогнозу серы», отдельно готовность расчёта и допустимость качества. Не объединять сверху синтетическую успешную рекомендацию и снизу hybrid-результат так, будто это одно решение. Показать, какой компонент реальный, какие свойства/потоки не подтверждены.

**Приёмка:** зритель не принимает `ready` за «смесь годна»; при неизвестных T95/CN не появляется утверждение о полном соответствии. Сохранить сценарий fail и понятное объяснение. Расширение физической модели перед сдачей не является обязательным способом закрытия этого замечания.

### AP-020 — P1. Описание, презентация и исполняемая версия не синхронизированы

**Подтверждено файлами и пересчётом.** DOCX на странице 1 и PPTX на слайде 1 ссылаются на `d0bbf23…`. Слайд 10 показывает UI от 11.09, старую навигацию и числа; оговорка есть, но это не демонстрация текущего продукта. В README/Q&A нет полноценного включения последних условий сдачи 18.09.

Числа пяти модельных примеров совпадают с текущей приёмкой — их не надо менять произвольно. Исторические frozen-метрики в DOCX подписаны как старые; также нельзя молча выдавать их за новое обучение. Но LIMS-результаты текущего запуска изменились: validation corrected MAE **1,65886 вместо 1,620**, coverage **89,372% вместо 88,89%**; test MAE **2,07476 вместо 2,002**, coverage **83,794% вместо 84,98%**. Разные версии необходимо явно разделить.

**Исправить:** после фиксации release обновить титулы, команды, список режимов, снимки UI, provenance чисел и матрицу ТЗ. Для каждого ML-числа хранить model_id, dataset_id, период, N, определение метрики и файл отчёта. Старый результат оставлять только как явно архивное сравнение. В DESIGN §16 поставить прямую пометку о замене старой семантики тегов уточнениями 15.09, а не заставлять читателя разрешать противоречие самому.

**Приёмка:** один источник чисел и один release commit для README, DOCX, PPTX и архива; все live-показанные значения совпадают; исследовательские ограничения сохранены. Новые документы не заявляют «полная проверка пройдена», ссылаясь только на пять synthetic-сценариев.

### AP-021 — P1. Готовность на чужой машине и offline ещё не доказана

**Пробел приёмки, не воспроизведённая сетевая ошибка.** Сейчас доказана работа отдельных путей в окружении автора. Проверка старого архива использовала ту же установленную `.venv`. Зелёный `pip check` не означает, что зависимости можно установить на любой ОС или что каталог виртуального окружения переносим.

**Сделать:** отдельный прогон именно финального release на новой папке/профиле или машине. Подготовить зависимости заранее для offline-демо. Если заявлена установка без сети, приложить совместимые wheel-файлы/установщик; если только работа без сети после установки, именно так и написать. Зафиксировать ОС, Python, команды, длительность, отсутствие внешних обращений и результаты.

**Приёмка:** весь основной показ проходит без интернета и без обращения к рабочим каталогам автора; отсутствующие данные/модель дают инструкцию восстановления, а не traceback. Нельзя закрыть этот пункт формулировкой «в коде нет requests».

### AP-022 — P2. Размеры и управление окнами требуют отдельной финальной проверки

**Частично наблюдалось, полная матрица не пройдена.** Приложение задаёт 1536×1024 при логическом экране Tk 1536×960 на машине проверки, минимум 1120×760. В сценах есть широкие таблицы, длинные пути и непереносимые подписи. Это риск ухода важных элементов за рабочую область, особенно при масштабировании Windows.

Не считать текущие screenshots окончательной визуальной приёмкой. Визуальная проверка «История/ML» требует повторения без параллельного пользовательского переключения вкладок.

**Проверить и исправить по результату:** стартовое окно помещается в рабочую область; весь текст и кнопки доступны на 1366×768 и 1920×1080, 100% и 125–150%; таблицы и длинные поля прокручиваются; Tab/Enter работают; модальные окна можно закрыть; tooltip/подробности раскрывают длинные единицы и причины. Время/модель не исчезают за правым краем.

**Приёмка:** на целевом ноутбуке и проекторе выполнен весь сценарий без ручного растягивания окна для поиска кнопки. Ошибки и ограничения не различаются только цветом. Сохранены новые корректные снимки всех основных состояний.

## 6. Существующие вопросы, которые остаются существенными

- **AP-005:** отличать validation-метрики выбора до refit от оценки artifact на данных его финального обучения. Это не автоматически обвинение в использовании test для выбора; нужна правильная маркировка доказательств.
- **AP-007:** нулевой одинаковый риск и одинаковая масса партии не демонстрируют содержательный компромисс по надёжности/выпуску. Минимум — честно пояснить фактически работающие критерии и показать альтернативы; дополнительный synthetic-пример полезен, но не оправдывает выдуманные заводские нормы.
- **AP-008:** подготовка полного набора и отдельные replay выполнены в этом аудите, LIMS-коррекция пересчитана; **полный исторический аудит финальной версии всё ещё не выполнен**. Нужны нормальный, рискованный и неполный исторические срезы, размеры, доли отказов, baseline и покрытие.
- **AP-009:** выбор произвольного интервала — отдельный незакрытый пункт Q&A. Один timestamp и выбор train/test не эквивалентны пользовательскому периоду.

## 7. Каким должен стать понятный UI

Не нужен полный редизайн. Достаточно устранить разрыв между вычислениями и пользовательскими действиями.

### Первый экран

Человек видит: «Локальный прототип. Реальные уставки не изменяются», готовность данных и три ясно названных режима. Для первого знакомства предложен модельный пример без ожидания полной истории. Для истории — готовые проверенные примеры и возможность выбрать момент/интервал. Исследования доступны отдельно.

### Единая структура результата

1. **Контекст:** режим, источник данных, момент и timezone, горизонт, модель, дата расчёта.
2. **Что обнаружено:** конкретная проблема или отсутствие необходимости менять рецепт.
3. **Результат:** рекомендация внутри модели / сохранить / действие не рекомендуется / техническая ошибка.
4. **Числа:** факт отдельно от прогноза; point отдельно от upper/lower; исходно → выбранный вариант; единицы и массовая база.
5. **Проверки:** выполнено / нарушено / неизвестно; фактическое значение, предел, основание.
6. **Объяснение и следующий шаг:** почему выбран вариант или чего не хватает; понятные альтернативы.
7. **Доказательство:** открыть запуск, сохранить краткий результат, выгрузить полный журнал.

После изменения входов ранее рассчитанный результат остаётся доступным, но явно обозначается как относящийся к прежним параметрам. Во время расчёта кнопка не должна молча запускать множество одинаковых задач. Закрытие экрана не уничтожает полученный результат и не вызывает ошибку.

### Что убрать с основного маршрута, не удаляя функциональность

- Свободное редактирование служебных hashes/ID и выбор любых experimental-моделей.
- Обучение и тяжёлые исследовательские сравнения перед первым результатом.
- Подачу технического JSON как единственного объяснения.
- Историю Stage 0–10 перед инструкцией запуска.
- Несколько разных кнопок «прогноз», различие которых нужно выяснять по коду.

выбор release-контекста, сборщик и сопровождающие документы. Это проверка
изменений после аудита, не новая независимая оценка ML на всём периоде.

Исправленные регрессии:

- **AP-011:** отсутствие файла закреплённой модели или dataset больше не
  разрешает UI молча выбрать другой доступный артефакт. Action-study исключён
  из каталога обычных forecast-моделей.
- **AP-009 / AP-018:** интервальный результат теперь сохраняется при навигации
  и экспортируется вместо предыдущего одиночного прогноза. На время нового
  запроса экспорт старого результата отключён. Hybrid восстанавливает показанный
  результат при возвращении на страницу.
- **AP-009:** dataset и доверенная модель загружаются один раз на интервал,
  а не заново для каждой точки. Каждая точка по-прежнему проходит `run_cycle`
  со своим временем и отдельным контекстом. Coverage не считает пустую оценку
  серы доступным прогнозом.
- **AP-012 / AP-014:** сборщик запускает acceptance из копии поставки, не из
  исходного checkout; старый отчёт больше не подставляется вместо проверки.
  Добавлены документы по ссылкам README, проверка ошибок Git и точное описание
  состава manifest/SHA256SUMS.
- Исправлены ошибки статической проверки типов в новых interval/UI участках.

Регрессионные проверки включают настоящий скрытый Tk: расчёт интервала,
переход на журнал и обратно, сверку экспортированного JSON. Видимое окно
пользователя не использовалось. Старый архив v9 не содержит этих последующих
исправлений: его прежние результаты проверки нельзя переносить на новый код.

Ограничения AP-005/AP-007/AP-008 и запрет реального управления сохраняются.
Холодная установка зависимостей на другом ПК и полная ручная оценка удобства
интерфейса этим повторным ревью не заменяются.

Проверка исправленного checkout: `pytest -q` — **169 passed**, `ruff check source
global_tests` — без ошибок, `mypy source` — без ошибок в 34 файлах. Единственное
предупреждение pytest относится к будущему поведению стандартного `tarfile`.

После сборки проверен `output/reviewed-release-2026-09-21-r2.zip`: 166/166
SHA-256 совпали, исходники исправленных модулей совпадают с checkout, пять
acceptance-эпизодов завершились ожидаемыми статусами. Из каталога поставки
выполнен реальный interval replay 01.06.2025 12:00–13:00 +03:00: две точки,
coverage 1.0, два `abstain` (реальные действия выключены), около **62 секунд**.

**Оставшийся недостаток AP-009:** удаление повторных загрузок не устранило
стоимость самого прогноза. Для длинного интервала нужны отдельное профилирование,
индикатор прогресса и отмена; текущая форма не показывает ход расчёта по точкам.
Для защиты выбирать короткий интервал и предупреждать о времени ожидания.
