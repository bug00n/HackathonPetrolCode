# Гайд по проекту HackathonPetrolCode

Этот файл - входная дверь в проект. Он написан для ситуации, когда ты открыл
репозиторий и пока не понимаешь ни нефтяную предметку, ни зачем тут столько DTO,
ни почему нельзя просто обучить модель и вывести число.

Главная мысль:

```text
Мы строим безопасный и воспроизводимый контур принятия решения для оператора.
```

Система должна не только посчитать рекомендацию, но и доказать:

- какие данные были доступны на момент решения;
- какие варианты действий рассматривались;
- какие ограничения были проверены;
- почему выбранный вариант допустим;
- почему система отказалась, если надежного варианта нет.

---

## 1. Что просит ТЗ

ТЗ описывает производство товарного дизельного топлива как цепочку:

```text
АВТ -> гидроочистка -> блендинг
```

Расшифровка:

- `АВТ` - первая стадия, где сырье разделяется на фракции.
- `Гидроочистка` - стадия, где продукт очищают, в том числе снижают серу.
- `Блендинг` - смешение компонентов для получения товарного дизельного топлива.

Главное жесткое ограничение:

```text
сера товарного дизельного топлива <= 10 мг/кг
```

Команда должна сделать мультиагентную систему. В нашем проекте это не LLM и не
микросервисы, а несколько логических ролей в обычном Python-коде:

- агент качества;
- агент надежности;
- агент оптимизации;
- оркестратор.

Оператор должен увидеть не магию, а понятную цепочку:

```text
состояние -> оценки -> кандидаты -> ограничения -> рекомендация или отказ
```

---

## 2. Что считается хорошим результатом

Хорошая система:

- синхронизирует источники по времени;
- не использует будущие данные;
- явно хранит единицы измерения;
- сохраняет источник каждого значения;
- отличает "данных нет" от "все хорошо";
- не выбирает кандидата, который нарушает жесткое ограничение;
- умеет ответить `hold`, `recommend` или `abstain`;
- пишет журнал, чтобы решение можно было проверить.

Плохая система:

- подмешивает будущие лабораторные анализы;
- молча округляет `10.0001` до `10`;
- считает `unknown` успешной проверкой;
- рекомендует реальные уставки без доказанной модели последствий;
- показывает в UI числа, которые не прошли общий backend-cycle.

## 3. Источники данных

Основные материалы лежат в `materials/`.

### Телеметрия

`materials/data.rar` содержит:

- `data/avt_tags.csv`;
- `data/242000_tags.csv`.

Это технологические временные ряды. Временной ключ - `date`. Служебные колонки
`Unnamed: ...` надо игнорировать.

### ЛИМС

ЛИМС - лабораторные анализы. Они редкие, но считаются контрольным фактом по
качеству.

Важная временная особенность: анализ мог быть взят в 12:00, но доступен системе
только позже. Сейчас задержка задана в `config/runtime.toml`:

```toml
lims_delay_hours = 6.0
```

### ПАК

ПАК - поточные анализаторы. Они оперативнее лаборатории, но могут ломаться или
расходиться с ЛИМС.

Приоритет источников качества:

```text
ЛИМС -> ПАК -> ВАК
```

### Справочник тегов

`materials/Теги_хакатон.xlsx` и нормализованный `config/tags.csv` описывают:

- исходное имя тега;
- физический смысл;
- единицу;
- стадию процесса;
- подтвержден ли mapping;
- можно ли считать тег управляемым.

Нельзя угадывать смысл тега по короткому имени.

## 4. Backend и ML

В проекте два направления.

Backend отвечает за:

- DTO-контракты;
- чтение и нормализацию данных;
- временную семантику;
- сбор состояния на момент времени;
- CLI и будущий UI;
- orchestration;
- единые hard constraints;
- журналирование;
- интеграцию ML-артефактов;
- тесты backend-поведения.

ML отвечает за:

- смысл тегов;
- признаки;
- формулы ВАК;
- прогноз качества;
- неопределенность;
- модель последствий действий;
- выбор и обоснование управляемых параметров;
- отчеты с метриками.

Правило:

```text
ML задает численную семантику, backend обеспечивает безопасное единое применение.
```

Если ML-модель не доказала, что умеет оценивать действия, backend не должен
превращать обычный прогноз в рекомендацию поменять уставки.

## 7. Главные DTO

Все ключевые типы лежат в `source/contracts.py`.

### `RuntimeConfig`

Настройки запуска: часовой пояс, задержка ЛИМС, свежесть источников, горизонт,
пути к данным/моделям/журналам.

### `ScenarioConfig`

Сценарий решения: режим, обязательные сигналы, constraints, компоненты
блендинга, текущая рецептура, критерии и допущения.

### `Observation`

Одно измерение с полями:

- `measured_at` - когда измерили;
- `available_at` - когда стало доступно системе;
- `value`;
- `unit`;
- `validity`;
- `source_ref`.

### `ProcessState`

Состояние процесса на момент `as_of`. Содержит только то, что можно было знать
на этот момент.

### `CandidateAction`

Кандидат действия:

- `hold` - ничего не менять;
- `blend` - изменить рецептуру;
- `setpoints` - изменить уставки, но в stage 1 реальные setpoints выключены.

### `AgentAssessment`

Ответ агента по кандидату: метрики, issues, статус.

### `ConstraintResult`

Результат hard-check:

- `pass`;
- `fail`;
- `unknown`.

Важно:

```text
unknown != pass
```

### `Recommendation`

Итог цикла:

- `hold`;
- `recommend`;
- `abstain`.

## 8. Как работает stage-1 cycle

Упрощенно:

```text
run_cycle
  -> build state
  -> generate_candidates
  -> evaluate_candidates
       -> agent assessments
       -> check_constraints
  -> select hold/recommend/abstain
  -> build_explanation
  -> write_run_journal
  -> return Recommendation
```

В `model_demo` каждый кандидат оценивается через:

```text
assess_blend_candidate(state, candidate, scenario)
```

В `history/hybrid` stage 1 пока поддерживает только безопасный путь без модели
действий. Это специально: лучше честно ограничить возможности, чем изображать
реальное управление без доказательств.

## 9. Как читать demo-result

В JSON результата смотри на:

- `status` - главный итог;
- `baseline` - текущий режим, обычно `hold`;
- `selected` - выбранный кандидат;
- `checks` - какие ограничения прошли или упали;
- `reason_codes` - коды причин;
- `explanation` - человеческое объяснение;
- `run_id` - папка журнала в `runs/<run_id>/`.

Пример смысла:

```text
blend_risk:
baseline не проходит sulfur constraint,
selected проходит,
поэтому status = recommend.
```

### Этап 0 - данные и правила

Сделать единый язык данных: DTO, теги, время, источники, валидность.

Статус: реализовано.

### Этап 1 - первый сквозной прототип

Чистый запуск, понятный README, воспроизводимая демонстрация, финальные отчеты.

## 11. Как понимать rebase и конфликты в этом проекте

Если `dev` и твоя ветка одновременно добавили один и тот же файл, Git показывает
`add/add conflict`.

В этом проекте нельзя автоматически выбирать "мою" или "их" сторону. Нужно
смотреть, какая версия лучше соответствует `DESIGN.md`.

Правило:

```text
Если dev уже содержит более сильную доменную реализацию,
stage-ветка интегрируется вокруг нее, а не перетирает ее.
```

Для текущего rebase это означает:

- `effects.py`, `quality.py`, `reliability.py` берем из `dev`;
- `optimizer.py` объединяем;
- `orchestrator`, `constraints`, `journal`, `explain`, CLI и tests сохраняем из
  stage 1.

После разрешения конфликтов обязательно:

```bash
rg "<{7}|={7}|>{7}" source README.md STAGE1.md PROJECT_GUIDE.md
python -m ruff check .
python -m mypy source
python -m pytest
```
