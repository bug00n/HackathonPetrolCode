# Гайд по проекту HackathonPetrolCode для полного погружения

Этот документ написан как входная дверь в проект. Его цель - не заменить
`DESIGN.md` и `IMPLEMENTATION_PLAN.md`, а объяснить человеческим языком:
что мы вообще строим, зачем это нужно, где backend, где ML, какие объекты уже
есть в коде и как постепенно двигаться по этапам.

Если коротко: мы делаем прототип системы, которая смотрит на состояние
производства дизельного топлива, оценивает риск проблем с качеством и предлагает
оператору безопасное действие. Если безопасного действия нет или данных не
хватает, система должна честно отказаться от рекомендации.

---

## 1. Суть проекта в одну минуту

Есть производство товарного дизельного топлива. В ТЗ оно рассматривается как
цепочка:

```text
АВТ -> гидроочистка -> блендинг
```

Что это значит:

- `АВТ` - начальная технологическая стадия, где сырье разделяется на фракции.
- `Гидроочистка` - стадия, где продукт очищают, в том числе снижают серу.
- `Блендинг` - смешение компонентов, чтобы получить товарный продукт.

Самое важное качество из ТЗ: для товарного дизельного топлива содержание серы
должно быть не больше:

```text
10 мг/кг
```

Система должна помогать оператору:

- понять текущее состояние;
- понять риск нарушения качества;
- сравнить возможные действия;
- выбрать безопасную рекомендацию;
- объяснить, почему выбран именно этот вариант;
- отказаться, если нельзя рекомендовать надежно.

Ключевой принцип ТЗ:

```text
Безопасность и качество важнее экономики.
```

То есть нельзя сказать: "да, сера выше нормы, зато выпуск больше". Такой вариант
должен быть отброшен.

## 2. Что от команды требует ТЗ

ТЗ просит построить мультиагентную систему. Здесь слово "агенты" не означает,
что обязательно нужен LLM, отдельные микросервисы или сложный фреймворк. В
нашем проекте агент - это логическая роль в коде.

Минимальный цикл из ТЗ:

1. Получить актуальное состояние процесса из телеметрии и анализов.
2. Проверить полноту, свежесть и согласованность данных.
3. Оценить текущее и прогнозное качество продукта.
4. Оценить тяжесть режима или риск для оборудования.
5. Сформировать несколько допустимых вариантов действий.
6. Отбросить варианты, нарушающие жесткие ограничения.
7. Сравнить оставшиеся варианты по критериям.
8. Выдать рекомендацию оператору или объясненный отказ.

В демонстрации нужно показать:

- нормальный период, где система не дергает оператора лишними действиями;
- период с риском ухудшения качества;
- ситуацию с неполными или устаревшими данными;
- полный путь от входных данных до итоговой рекомендации.

Оцениваться будет не только точность модели. Будут смотреть на:

- работу с данными;
- отсутствие временной утечки;
- понятность единиц измерения;
- качество прогноза;
- разделение ролей агентов;
- безопасность оптимизации;
- объяснимость результата;
- воспроизводимый запуск.

## 3. Какие данные есть в проекте

Основные материалы лежат в `materials/`.

### `materials/data.rar`

Архив с технологической телеметрией:

- `data/avt_tags.csv` - телеметрия АВТ;
- `data/242000_tags.csv` - телеметрия гидроочистки.

Это временные ряды примерно с шагом 10 минут. Временной ключ - колонка `date`.
Служебные колонки вида `Unnamed: ...` нужно игнорировать.

### `materials/ЛИМСы ...xlsx`

Лабораторные анализы качества. Это редкие измерения, они приходят асинхронно.
ЛИМС считается контрольным фактом, если он расходится с ПАК.

Важный момент: лабораторный анализ не становится доступным мгновенно. В текущей
конфигурации мы считаем, что ЛИМС доступен через 6 часов после отбора:

```toml
lims_delay_hours = 6.0
```

### `materials/Выгрузка ПАК ...xlsx`

ПАК - поточные анализаторы. Они дают более оперативные данные, но могут ломаться
или расходиться с лабораторией.

### `materials/Теги_хакатон.xlsx`

Справочник тегов. Из него нужно понимать:

- что означает тег;
- в каких единицах измеряется;
- можно ли считать его управляемым параметром;
- где источник подтверждения.

Нельзя угадывать физический смысл тега только по короткому имени.

### `config/tags.csv`

Текущий нормализованный словарь тегов для кода. Это уже stage-0 артефакт. Он
помогает backend не гадать, а работать с проверенными `signal_id`.

## 4. Кто такой пользователь системы

Пользователь - оператор или человек, принимающий технологическое решение.

Ему не нужен огромный JSON ради JSON. Ему нужно понять:

- что сейчас происходит;
- есть ли риск;
- что предлагается сделать;
- почему это безопасно;
- какие ограничения проверены;
- насколько свежие данные;
- почему система отказалась, если отказалась.

Поэтому backend обязан не просто вернуть числа, а сохранить и показать логику
решения.

## 5. Backend и ML: кто за что отвечает

В проекте два направления:

```text
Backend - контракты, данные, запуск, интеграция, UI, журнал, safety checks.
ML      - признаки, модели, формулы, численная оценка, отчеты по качеству.
```

### Backend отвечает за

- чтение исходников;
- нормализацию данных;
- временную семантику;
- DTO-контракты;
- загрузку конфигов;
- построение состояния на момент времени;
- запуск одного цикла решения;
- единое применение ограничений;
- журналирование;
- CLI;
- будущий Streamlit UI;
- интеграцию ML-артефактов;
- тесты своей части.

### ML отвечает за

- смысл тегов;
- выбор признаков;
- проверку формул ВАК;
- обучение моделей;
- оценку неопределенности;
- выбор допустимых управляемых параметров;
- оценку применимости модели;
- отчеты по качеству;
- доказательство, что модель можно использовать для сравнения действий.

### Главное правило взаимодействия

ML может придумывать и проверять гипотезы в своей ветке. Но если результат нужен
backend, он должен прийти через общий контракт:

- какие входы нужны;
- какие выходы возвращаются;
- какие единицы;
- какой `model_id`;
- какие ограничения применимости;
- какие тестовые ожидания.

Backend не должен тайно дублировать ML-логику в UI. ML не должен писать второй
production-загрузчик данных в ноутбуке.

Проверка:

```bash
python -m source.main validate-stage0
```

```text

3 model-demo fixture
170 тегов
```

Реализовано:

- `source/orchestrator.py` - один цикл принятия решения;
- `source/agents/quality.py` - агент качества;
- `source/agents/reliability.py` - агент надежности;
- `source/agents/optimizer.py` - генерация и оценка кандидатов;
- `source/agents/effects.py` - прозрачные demo-эффекты блендинга;

Важно: stage 1 пока не является промышленной ML-рекомендацией. Это исполняемый
backend-контур, куда потом можно подключать настоящие ML-модели.

### Stage 2: подготовка реальных данных

Реализовано:

- CLI-команда `prepare`;
- запись `data/processed/<dataset_id>/`;
- сохранение `manifest.json`;
- сохранение `telemetry.csv.gz`, `quality.csv.gz`, `issues.csv.gz`;
- сохранение `feature_order.json`;
- загрузка prepared dataset обратно через `load_prepared_dataset`;
- CLI-команда `build-state`;
- сбор `ProcessState` для сценария `history` из подготовленных данных;
- тесты `global_tests/test_stage2_data.py`;
- документация `STAGE2.md` и `CODE_WALKTHROUGH.md`.

Важно: stage 2 не обучает ML-модель и не делает промышленную рекомендацию. Он
делает входную data-границу воспроизводимой, чтобы ML и backend работали на одном
подготовленном датасете.

## 7. Что можно сделать программой прямо сейчас

Все команды запускаются из корня проекта.

### Проверить конфиги и контракты

```bash
python -m source.main validate-stage0
```

### Запустить нормальный demo-сценарий

```bash
python -m source.main run-model-demo blend_normal
```

Ожидаемый статус:

```text
hold
```

Это означает: текущая рецептура проходит ограничение по сере, менять ничего не
нужно.

### Запустить demo-сценарий с риском

```bash
python -m source.main run-model-demo blend_risk
```

Ожидаемый статус:

```text
recommend
```

Текущая рецептура нарушает ограничение, поэтому система выбирает допустимый
вариант. Сейчас это модельный блендинг, а не реальное управление установкой.

### Запустить demo-сценарий с нехваткой данных

```bash
python -m source.main run-model-demo blend_missing
```

Ожидаемый статус:

```text
abstain
```

Это означает: надежной рекомендации нет. Данных недостаточно, и система не имеет
права делать вид, что все нормально.

### Где смотреть журнал

После demo-запуска создается папка:

```text
runs/<run_id>/
```

В ней:

- `metadata.json` - общая информация о запуске;
- `input.json` - состояние, сценарий, контекст;
- `features.json` - пока пустой список признаков для stage 1;
- `trace.jsonl` - trace цикла;
- `candidates.jsonl` - все кандидаты и их проверки;
- `result.json` - итоговая рекомендация.

Папка `runs/` не коммитится.

### Подготовить оригинальные данные

```bash
python -m source.main prepare --materials materials --config config/runtime.toml
```

Команда пишет prepared dataset в `data/processed/<dataset_id>/` и печатает
короткий JSON-summary: `dataset_id`, путь, количество строк, диапазоны времени и
число issues.

### Собрать состояние на исторический момент

```bash
python -m source.main build-state --dataset data/processed/<dataset_id> --scenario history --as-of 2025-01-15T10:00:00+03:00
```

Команда печатает валидный `ProcessState`: что backend знает на момент `as_of`.
Если значение ещё не было доступно, оно не попадёт в selected observation.

## 9. Главные объекты проекта

Большинство важных типов описано в `source/contracts.py`. Это общий язык backend
и ML. Если ты понимаешь эти объекты, ты понимаешь скелет проекта.

### `RuntimeConfig`

Общие настройки запуска.

Примеры полей:

- `source_timezone`;
- `lims_delay_hours`;
- `freshness_minutes`;
- `horizon_minutes`;
- `max_candidates`;
- пути к данным, моделям, отчетам и журналам.

Загружается из:

```text
config/runtime.toml
```

### `ScenarioConfig`

Описание сценария решения.

В нем лежит:

- `id`;
- режим работы: `history`, `model_demo`, `hybrid`;
- обязательные сигналы;
- ограничения;
- компоненты блендинга;
- текущая рецептура;
- активные критерии;
- допущения.

Примеры:

```text
config/scenarios/history.json
config/scenarios/blend_normal.json
config/scenarios/blend_risk.json
config/scenarios/blend_missing.json
```

### `TagMeta`

Одна строка словаря тегов.

Говорит:

- исходное имя тега;
- нормальный `signal_id`;
- стадия: `avt`, `ht`, `blend`;
- физический смысл;
- единица;
- подтвержден ли mapping;
- можно ли управлять этим сигналом.

### `Observation`

Одно измерение.

Примерно:

```text
сигнал ht:2:Mg.Sulfur
источник lims
измерено в 12:00
доступно в 18:00
значение 8.4 мг/кг
валидность valid
source_ref: откуда именно взяли
```

Важная идея: `measured_at` и `available_at` разные. Это защищает от временной
утечки.

### `SignalSnapshot`

Снимок одного сигнала на момент решения.

Содержит:

- выбранное наблюдение;
- альтернативные наблюдения;
- возраст;
- свежесть;
- проблемы по сигналу.

### `ProcessState`

Состояние процесса на момент `as_of`.

Это не вся история, а только то, что было доступно системе в конкретный момент.

Содержит:

- `state_id`;
- `as_of`;
- `dataset_id`;
- `mode`;
- `signals`;
- `issues`.

### `CandidateAction`

Кандидатное действие.

Может быть:

- `hold` - ничего не менять;
- `setpoints` - поменять уставки;
- `blend` - поменять рецептуру блендинга.

В stage 1 реально используется:

```text
hold
blend
```

Реальные `setpoints` пока отключены, потому нет подтвержденной ML-модели
последствий.

### `MetricEstimate`

Оценка одной метрики.

Например:

```text
sulfur = 8.4 мг/кг
upper = 9.4 мг/кг
basis = formula
interval_kind = scenario_bound
```

Важно:

- `value` - центральная оценка;
- `upper` - верхняя оценка;
- если требуется safety, часто проверяем именно `upper`;
- `basis` говорит, откуда число: измерение, прогноз, формула, proxy.

### `AgentAssessment`

Ответ одного агента по одному кандидату.

Например агент качества возвращает:

```text
candidate_id = blend_A090_B010
metrics["sulfur"] = ...
status = ok
issues = []
```

### `ConstraintSpec`

Описание ограничения из сценария.

Например:

```text
metric = sulfur
upper = 10
unit = mg/kg
use_upper_estimate = true
required = true
```

### `ConstraintResult`

Результат проверки ограничения для кандидата.

Может быть:

- `pass`;
- `fail`;
- `unknown`.

Критически важно:

```text
unknown не равно pass
```

Если обязательное ограничение нельзя проверить, рекомендацию выдавать нельзя.

### `CandidateEvaluation`

Полная оценка кандидата:

- само действие;
- оценки агентов;
- проверки constraints;
- допустим ли кандидат;
- ключ ранжирования.

### `Recommendation`

Итог одного цикла.

Статусы:

- `recommend` - есть допустимое действие, и оно выбрано;
- `hold` - текущий режим допустим, лучше ничего не менять;
- `abstain` - надежной рекомендации нет.

### `RunFailure`

Техническая ошибка. Например сломался файл, модель несовместима, журнал не
записался.

Важно не путать:

```text
abstain    - технологический отказ: данных/вариантов не хватает.
RunFailure - техническая ошибка программы.
```

## 10. Как сейчас работает `run_cycle`

Точка входа:

```python
run_cycle(
    data,
    as_of,
    model,
    scenario,
    config,
    context,
    run_dir,
)
```

Смысл аргументов:

- `data` - подготовленные данные; в `model_demo` может быть `None`;
- `as_of` - момент времени, на который принимаем решение;
- `model` - ML-модель; в stage 1 пока `None`;
- `scenario` - сценарий;
- `config` - runtime config;
- `context` - контекст прошлого решения;
- `run_dir` - куда писать журнал.

Упрощенный flow:

```text
run_cycle
  -> построить ProcessState
  -> generate_candidates
  -> evaluate_candidates
       -> predict_quality
       -> assess_reliability
       -> optimizer metrics
       -> check_constraints
  -> выбрать status: hold/recommend/abstain
  -> build_explanation
  -> write_run_journal
  -> вернуть Recommendation
```

В `model_demo` состояние строится из сценария, без pandas и без реальных
подготовленных таблиц. Это сделано специально: demo-сценарии должны запускаться
легко и стабильно.

## 11. Как читать текущий результат demo-запуска

Запусти:

```bash
python -m source.main run-model-demo blend_risk
```

В JSON смотри на поля:

### `status`

Главный итог.

```json
"status": "recommend"
```

Значит, система предлагает действие.

### `baseline`

Оценка текущего режима, то есть `hold`.

Если там:

```json
"feasible": false
```

текущий режим нарушает ограничения.

### `selected`

Выбранный кандидат.

Например:

```json
"blend_mass_fractions": {
  "A": 0.9,
  "B": 0.1
}
```

Это означает: для demo-сценария выбран блендинг 90% компонента A и 10% компонента
B.

### `checks`

Проверки ограничений.

Для серы нужно смотреть:

```json
"constraint_id": "blend_sulfur"
"status": "pass"
"actual": 9.4
"upper": 10.0
```

### `explanation`

Человеческое объяснение.

Примерно:

```text
текущий режим не проходит ограничения, выбранный вариант проходит
```

---

## 12. Почему нельзя сразу делать реальные рекомендации

Потому что в ТЗ есть безопасность, а не только оптимизация.

Чтобы рекомендовать реальное изменение уставок, нужно доказать:

- что тег действительно управляемый;
- какие у него допустимые пределы;
- какой максимальный шаг изменения;
- что модель умеет оценивать последствия действия;
- что нет временной утечки;
- что модель проверена на исторических изменениях;
- что ограничения интерпретируются корректно.

До этого реальные управляющие воздействия отключены. Это не слабость проекта, а
правильная safety-позиция.

## 13. Этапы реализации простыми словами

Ниже пересказ `IMPLEMENTATION_PLAN.md`, но на более прикладном языке.

### Этап 0 - согласовать данные и правила

Цель: сделать так, чтобы backend и ML говорили об одних и тех же данных.

Backend:

- читает CSV/Excel;
- приводит время к UTC;
- учитывает задержку ЛИМС;
- сохраняет источник каждого значения;
- помечает плохие или неоднозначные значения;
- строит `ProcessState`.

ML:

- разбирает смысл тегов;
- проверяет единицы;
- выбирает цели прогнозирования;
- смотрит расхождения ЛИМС/ПАК;
- определяет, какие сигналы можно использовать.

Готовность: один формат данных, один словарь, неподтвержденные управляющие теги
не используются.

Статус сейчас:

```text
реализовано
```

### Этап 1 - первый сквозной прототип

Цель: получить работающий цикл от состояния до объяснения.

Backend:

- делает `run_cycle`;
- подключает логические роли;
- реализует `hold/recommend/abstain`;
- пишет журнал;
- готовит минимальный UI или CLI.

ML:

- дает базовую оценку качества;
- дает простой индекс тяжести режима;
- готовит demo-сценарии;
- дает кандидаты, включая `hold`.

Готовность: можно показать полный цикл.

Статус сейчас:

```text
backend-каркас реализован для model_demo
Streamlit UI еще нет
```

### Этап 2 - прогноз серы

Цель: научиться прогнозировать серу гидроочищенного продукта на горизонте 60
минут.

Backend:

- загрузить ML-артефакт;
- проверить совместимость модели;
- проверить порядок признаков;
- показать прогноз, горизонт и причины недоверия.

ML:

- обучить baseline;
- сравнить модели;
- сделать временное train/validation/test разбиение;
- проверить ошибки около порога 10 мг/кг;
- сохранить модель и отчет.

Готовность: есть отчет с метриками и модель, которую backend может загрузить.

### Этап 3 - ограниченная оптимизация и надежность

Цель: сравнивать допустимые действия и не нарушать ограничения.

Backend:

- реализовать общий фильтр ограничений;
- сохранять причины отбраковки каждого кандидата;
- показывать текущее и рекомендуемое значение;
- показывать альтернативы.

ML:

- выбрать 2-3 подтвержденных управляющих параметра;
- описать диапазоны и шаги;
- проверить область применимости;
- ранжировать допустимые варианты.

Готовность: система находит допустимые варианты или честно отказывается.

### Этап 4 - связанная цепочка и блендинг

Цель: показать всю цепочку АВТ -> гидроочистка -> блендинг.

Backend:

- разделить исторические факты и модельные предположения;
- показать прохождение состояния по стадиям;
- показать происхождение свойств компонентов.

ML:

- учесть качество входящего потока;
- использовать массовые доли для серы смеси;
- проверять доступность компонентов;
- не усреднять сомнительные свойства без обоснования.

Готовность: видно, как качество компонента влияет на финальную рецептуру.

### Этап 5 - устойчивость и неопределенность

Цель: система должна быть надежной при плохих данных.

Backend:

- обрабатывать пропуски;
- обрабатывать устаревшие анализы;
- обрабатывать конфликты источников;
- не выдавать постоянно меняющиеся рекомендации;
- сохранять версии данных/модели/правил.

ML:

- оценить верхнюю границу серы;
- проверить покрытие этой границы;
- подобрать пороги существенности;
- проверить устойчивость к задержкам и ошибкам.

Готовность: нормальный период не вызывает лишних действий, плохие данные ведут к
снижению доверия или отказу.

### Этап 6 - приемка и демонстрация

Цель: другой человек может запустить проект и воспроизвести результат.

Backend:

- чистый запуск;
- понятный README;
- экспорт журнала;
- воспроизводимые demo-эпизоды.

ML:

- зафиксировать модели;
- показать итоговые метрики;
- объяснить ограничения;
- подготовить защиту.

Готовность: проект запускается по инструкции, результаты воспроизводимы.

- коммитит `runs/`, `.test_tmp/`, подготовленные CSV или модели;

## 17. Что важно не сломать

### Время

Нельзя использовать данные из будущего.

Если анализ был измерен в 12:00, но стал доступен в 18:00, то в решении на
14:00 его еще нельзя использовать.

### Единицы

Нельзя молча считать `ppm`, `% масс.` и `мг/кг` одним и тем же, если конвертация
не описана.

### Источники качества

Приоритет:

```text
ЛИМС -> ПАК -> ВАК
```

Но приоритет не означает, что можно игнорировать свежесть и доступность.

### Жесткие ограничения

Сера выше 10 мг/кг - это не "плохой score", а нарушение ограничения.

Нельзя выбрать кандидата, который нарушает обязательный constraint.

### `unknown`

Если constraint нельзя проверить, это не успех.

```text
unknown != pass
```

### Demo и реальность

`model_demo` - это модельный сценарий. Его нельзя продавать как реальный
промышленный совет.

## 18. Как устроены текущие stage-1 demo-сценарии

Есть два компонента:

```text
A
B
```

У каждого есть заданная сера:

- A: низкая сера;
- B: высокая сера.

Смесь считается по массовым долям:

```text
S_mix = w_A * S_A + w_B * S_B
```

Проверяется верхняя оценка серы:

```text
upper <= 10 мг/кг
```

### `blend_normal`

Текущая рецептура:

```text
A = 0.9
B = 0.1
```

Верхняя оценка серы:

```text
9.4 мг/кг
```

Результат:

```text
hold
```

### `blend_risk`

Текущая рецептура:

```text
A = 0.7
B = 0.3
```

Верхняя оценка серы:

```text
14.2 мг/кг
```

Это выше 10, значит `hold` недопустим.

Результат:

```text
recommend A=0.9, B=0.1
```

### `blend_missing`

У компонента A нет полной оценки серы.

Результат:

```text
abstain
```

## 19. Как работает ранжирование кандидатов

В design указан ключ:

```text
(risk_index, -throughput, cost_proxy, change_size, candidate_id)
```

Смысл:

1. меньше риск;
2. больше выпуск;
3. меньше cost proxy;
4. меньше изменение режима;
5. стабильный tie-breaker по id.

Но важный порядок такой:

```text
сначала constraints, потом ranking
```

Нельзя взять экономически лучший вариант, если он не прошел серу или запас
компонентов.

## 20. Почему нужен журнал

Журнал нужен, чтобы не было магии.

Когда система сказала `recommend`, мы должны доказать:

- какие входы были доступны;
- какие кандидаты рассматривались;
- какие метрики посчитали агенты;
- какие constraints прошли или упали;
- почему выбран именно этот кандидат;
- какой был итоговый JSON.

Без журнала демонстрация превращается в "поверьте, оно так посчитало".

## 21. Что такое "объяснимость" в этом проекте

Объяснимость - это не длинный красивый текст. Это возможность проверить цепочку:

```text
данные -> оценка -> ограничение -> выбор -> рекомендация
```

Хорошее объяснение оператору:

- короткое;
- говорит проблему;
- говорит действие;
- говорит ожидаемый эффект;
- говорит ограничения;
- говорит причины недоверия.

Пример хорошего отказа:

```text
Надежной рекомендации нет: последнее лабораторное значение устарело,
а доступные варианты нарушают ограничение по сере.
```

## 24. Как взаимодействовать с ML-человеком

Когда ML говорит "я сделал модель", backend должен спросить не "скинь pkl", а:

- какой `model_id`;
- какая версия схемы;
- какие входные признаки и порядок;
- какие единицы;
- какой горизонт прогноза;
- какой отчет качества;
- какие ограничения применимости;
- что ожидается на общей тестовой точке;
- поддерживает ли модель действия или только прогноз.

Если модель не поддерживает действия, backend может показывать прогноз, но не
должен рекомендовать изменение уставок как будто эффект доказан.

## 26. Как понимать статусы результата

### `hold`

Система говорит:

```text
текущий режим допустим, не надо лишний раз менять процесс
```

Это нормальный положительный исход.

### `recommend`

Система говорит:

```text
текущий режим плохой или есть существенное улучшение,
выбран допустимый вариант
```

### `abstain`

Система говорит:

```text
нет надежной рекомендации
```

Это тоже качественное поведение. В ТЗ прямо сказано, что система должна уметь
отказываться.

## 27. Частые ошибки мышления

### Ошибка 1: "Если данных нет, значит нарушений нет"

Нет. Если данных нет, значит мы не знаем. Это может привести к `abstain`.

### Ошибка 2: "Исторический min/max - это промышленный предел"

Нет. История показывает, где процесс был, но не доказывает допустимые границы.

### Ошибка 3: "Модель предсказывает серу, значит можно менять уставки"

Нет. Прогнозная модель и модель последствий действий - разные вещи.

### Ошибка 4: "UI может чуть-чуть пересчитать"

Нет. UI не должен быть вторым backend. Вся логика должна быть в общем цикле и
constraints.

### Ошибка 5: "Можно округлить 10.0001 до 10"

Нет. Ограничение проверяется до округления.

## 28. Мини-глоссарий

### ЛИМС

Лабораторные анализы. Редкие, но считаются контрольным фактом.

### ПАК

Поточные анализаторы. Частые и оперативные, но могут быть неисправны.

### ВАК

Виртуальный анализатор: расчетная формула или модель качества.

### КИП

Технологические датчики: температура, давление, расход, уровень и так далее.

### МАС

Мультиагентная система. В нашем проекте это несколько логических ролей в коде.

### Constraint

Жесткое ограничение. Если не пройдено, кандидат нельзя выбрать.

### Candidate

Вариант действия, который система оценивает.

### Baseline

Текущий режим, обычно кандидат `hold`.

### Provenance

Происхождение значения: из какого файла, строки, колонки или сценария оно взято.

## 32. Главная идея, которую нужно держать в голове

Мы не просто пишем код, который "что-то предсказывает".

Мы строим воспроизводимый и безопасный контур принятия решения:

```text
что известно -> насколько этому можно верить -> что можно сделать ->
что запрещено -> что лучше из разрешенного -> как объяснить человеку
```

Если ты реализуешь backend-задачу и после нее можно лучше ответить на этот путь,
ты двигаешь проект в правильную сторону.

Если задача добавляет красивые числа, но непонятно откуда они, почему им можно
верить и какие ограничения они прошли, это не закрывает ТЗ.

## 33. Как понимать rebase и конфликты в этом проекте

В этом проекте конфликты при rebase - это не просто техническая неприятность.
Они часто показывают, что две ветки одновременно уточняли одну и ту же часть
архитектуры.

Главное правило:

```text
если dev уже содержит более сильную доменную реализацию,
stage-ветка должна интегрироваться вокруг нее, а не перетирать ее
```

Например, в stage 1 после rebase с `dev` правильная стратегия такая:

1. Оставить из `dev` более зрелую доменную логику агентов:
   `effects.py`, `quality.py`, `reliability.py`.
2. Добавить вокруг нее недостающую stage-1 механику:
   генерацию кандидатов, оценку кандидатов, orchestration, CLI demo, журнал,
   тесты и документацию.
3. Не менять DTO-контракт без необходимости. Если сигнатуры не совпадают,
   лучше адаптировать `optimizer` или `orchestrator`, чем ломать
   `source/contracts.py`.
4. После разрешения конфликта проверить, что нет conflict markers:

```bash
rg "<{7}|={7}|>{7}" source README.md STAGE1.md PROJECT_GUIDE.md
```

Перед завершением backend-ветки нужно пройти короткий чеклист:

- `python -m ruff format .`;
- `python -m ruff check .`;
- `python -m mypy source`;
- `python -m pytest`;
- `python -m source.main validate-stage0`;
- demo-команды stage 1 возвращают ожидаемые статусы;
- stage-2 команды `prepare` и `build-state` работают на fixtures;
- `README.md`, `STAGE1.md`, `STAGE2.md`, `CODE_WALKTHROUGH.md` и этот гайд
  объясняют текущее состояние проекта;
- в коммит не попали `.test_tmp/`, `.pytest_cache/`, `.pytest_tmp/`, `runs/`,
  распакованные данные и случайные артефакты.
